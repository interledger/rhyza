# Rhyza Lite Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the full Rhyza stack (all 21 services plus Kafka, MongoDB, Valkey) in 1GB of RAM or less at idle after startup, for local dev, without changing any existing service or shared lib.

**Architecture:** A new package `rhyza-lite-service` imports every service's `service.ts` class and starts them in one Node process. They still talk over Kafka and gRPC on `localhost`. A new `docker/docker-compose.lite.yaml` runs that one container next to Kafka (heap capped) and MongoDB (cache capped). The runner container carries network aliases for every original service hostname, so env values and peer URLs stay the same as in `docker-compose.yaml`.

**Tech Stack:** TypeScript (repo `tsconfig.json`, CommonJS output, `module: NodeNext`), Node 24, pnpm workspaces, `node:test` via `node --import tsx --test`, Docker Compose, `@confluentinc/kafka-javascript` through `implementations-lib`.

**Spec:** `dev-docs/specs/2026-11-24-lite-mode-design.md`

## Global Constraints

- Budget: the sum of `docker stats --no-stream` memory across the lite containers, idle after startup, is 1GB or less (measured on the Linux containers, not native macOS).
- Existing files that may change: root `package.json` (new `lite:*` scripts), `docs/src/content/docs/testlocal.mdx` (new section), `packages/tests-e2e/index.test.ts` (optional env vars, defaults equal to today's values), and `pnpm-lock.yaml` (unavoidable, it's regenerated when the new workspace package is added). Nothing else existing changes: no services, no shared libs, no `docker-compose*.yaml`, no CI. If something can't work without one of those, stop and raise it.
- Kafka in lite: `KAFKA_HEAP_OPTS: "-Xmx256m -Xms256m"` as the starting value. MongoDB in lite: `--wiredTigerCacheSizeGB 0.25`.
- `RHYZA_SERVICES` defaults to all 21 service packages, `ase-mock-service` included.
- Topics and partition counts match the `init-kafka` script in `docker/docker-compose.yaml` exactly (3 partitions, `audits` and `logs` at the broker default of 1), replication factor 1.
- Readiness line: `Rhyza lite start complete`.
- Dev-only: no release or CI wiring.
- Work on branch `cozmin/rhyza-lite`. Conventional, lowercase commit summaries (`feat:`, `docs:`, `chore:`, `test:`). No `Co-Authored-By` or any Claude/Anthropic attribution in commits. No em-dashes in code, comments, docs or commits.
- Checked during planning: every service's default listen port is distinct and binds `0.0.0.0`, so 21 services fit in one process without `PORT`/`HOST`. Only the 3 PAL services call `OpenTelemetryService.Start`, and it throws on a second call, so the runner must create telemetry once and pass it in.
- Building `open-payments-resource-service` needs the submodule: run `git submodule update --init` once before any full build.

## Review Focus

1. A service's `start()` throws halfway through startup: the services already started get stopped in reverse order, and the process exits non-zero instead of hanging with live Kafka consumers. (Task 2 test `start failure stops already started services in reverse and rethrows`.)
2. SIGTERM arrives while startup is still in progress: no further services start, the started ones are stopped, and the process exits within 5s. (Task 2 test `stop during start prevents remaining services from starting`.)
3. `RHYZA_SERVICES` with a typo, extra whitespace, duplicates or an empty value: a typo fails fast and names the bad entry, whitespace is trimmed, duplicates collapse, and empty means the default. (Task 1 tests.)
4. The topic list drifts: someone adds a topic to `init-kafka` and lite mode silently lacks it. (Task 3 test `lite topics match init-kafka in docker-compose.yaml`.)
5. Restarting the stack with topics already present (`docker compose stop` then `start`, so Kafka keeps its data): topic creation must not fail. (Task 5 verification step 7.)

### Task 2: LiteRunner (ordered start, reverse stop)

**Files:**

- Create: `packages/rhyza-lite-service/src/runner.ts`
- Test: `packages/rhyza-lite-service/test/runner.test.ts`

**Interfaces:**

- Produces, in `runner.ts`:
  - `export interface LiteServiceEntry { readonly name: string; start(): Promise<void>; stop(): Promise<void>; }`
  - `export class LiteRunner { constructor(entries: readonly LiteServiceEntry[], logger: ILogger); start(): Promise<void>; stop(): Promise<void>; }` (`ILogger` from `common-types-lib`)
- Behavior:

  - `start()` starts entries one at a time, in the given order, awaiting each. If one throws, it stops the already-started entries in reverse order, then rethrows the original error.
  - `stop()` stops started entries in reverse order. If one `stop()` throws, it logs and continues with the rest. Calling `stop()` while `start()` is in flight marks the runner stopping: the in-flight entry finishes starting, no further entries start, and everything started gets stopped. `start()` then resolves without throwing. Calling `stop()` twice is a no-op the second time.

- [ ] **Step 1: Write the failing tests**

Use a helper `createEntry(name, calls, options?)` that pushes `start:<name>` and `stop:<name>` into a shared `calls: string[]`, with options `failStart`, `failStop`, and `startGate?: Promise<void>` (start awaits it). Use a silent logger stub implementing `ILogger`'s methods as no-ops (`child()` returns itself).

```ts
test('starts in order and stops in reverse', async () => {
  // entries a, b, c -> start() then stop()
  assert.deepEqual(calls, [
    'start:a',
    'start:b',
    'start:c',
    'stop:c',
    'stop:b',
    'stop:a'
  ]);
});
test('start failure stops already started services in reverse and rethrows', async () => {
  // a, b(failStart: new Error('boom')), c
  await assert.rejects(runner.start(), { message: 'boom' });
  assert.deepEqual(calls, ['start:a', 'start:b', 'stop:a']);
});
test('stop continues past a failing stop', async () => {
  // a, b(failStop), c -> start, stop resolves
  assert.deepEqual(calls.slice(3), ['stop:c', 'stop:b', 'stop:a']);
});
test('stop during start prevents remaining services from starting', async () => {
  // a, b(startGate), c; call start() without awaiting, then stop(), then release gate
  assert.deepEqual(calls, ['start:a', 'start:b', 'stop:b', 'stop:a']);
});
test('second stop is a no-op', async () => {
  // a -> start, stop, stop
  assert.deepEqual(calls, ['start:a', 'stop:a']);
});
```

    - `PalLedgerCommandHandlerService.start(undefined, factory, undefined, undefined, undefined, undefined, telemetry)`

  1. `selectServices(process.env['RHYZA_SERVICES'])`.
  2. Logger `new PinoLogger({ bcName: 'LITE', appName: 'RHYZA_LITE_SVC', instanceId })`, with `instanceId = RHYZA_LITE_SVC_<uuid>`.
  3. Telemetry: `OpenTelemetryService.Start('LITE', 'RHYZA_LITE_SVC', <package version>, instanceId, logger, process.env['OPEN_TELEMETRY_COLLECTOR_URL'] || 'http://127.0.0.1:4317')`, then `OpenTelemetryService.getInstance()`. The default matches the PAL services' default.

  7. SIGINT/SIGTERM: `runner.stop()`, with a 5s timer that force-exits with 99, then `process.exit()`. On `uncaughtException`, log and `process.exit(999)`, as in the services' `index.ts`.
