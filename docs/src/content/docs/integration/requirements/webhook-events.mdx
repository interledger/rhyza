The main communication channel between an FSP and their Rhyza instance consists of the Admin API and webhook events sent by the `notifications` service.

:::note
Rhyza doesn't hold account balances for an FSP's users/customers. Instead, it tracks the liquidity of the FSP's internal peer accounts in its own database.
:::

## Specify a webhook endpoint

For Rhyza to notify an FSP about webhook events, the FSP must expose a webhook endpoint that listens for the dispatched events. The events provide time-sensitive status updates, warnings, and errors so that the FSP can react accordingly.

The webhook endpoint URL is configured using the `WEBHOOK_URL` environment variable.

When an event occurs, the `notifications` service makes request to the configured endpoint. The service expects a `200` status in return.

<div class="overflow-table">

| Variable      | Type            | Description                                                       |
| ------------- | --------------- | ----------------------------------------------------------------- |
| `WEBHOOK_URL` | `notifications` | The endpoint where requests are made when a webhook event occurs. |

</div>

## Webhook event request body

Each webhook event is sent as a JSON payload with the following structure in the request body. The parameters in the `data` object vary depending on the event.

<div class="overflow-table">

| Attribute | Type   | Description                                        | Required |
| --------- | ------ | -------------------------------------------------- | -------- |
| `id`      | String | UUID for the event                                 | Y        |
| `type`    | Enum   | The event type                                     | Y        |
| `data`    | Object | Additional data that coincides with the event type | Y        |

</div>

:::tip[Duplicate events]
The `id` in the webhook event payload is unique. An FSP can use the ID to determine whether the event was previously received, preventing duplicate event processing.
:::

We provide an <LinkOut href="https://github.com/interledger/rafiki-v2/blob/main/docs/openapi/webhooks.yaml">OpenAPI specification</LinkOut> for the webhook events fired by Rhyza.

Additionally, the [Local Playground](/integration/playground/overview) contains example payloads in the <LinkOut href="https://github.com/interledger/rafiki-v2/blob/main/bruno/collections/rafiki-v2/Sample%20Webhook%20Events">Bruno collection</LinkOut> that can be used to test an FSP's webhook service integration.

## Event handling

### Asynchronous handling

If requests to credit/debit user accounts are lengthy processes, we recommend using a worker to process received events. The worker allows the server to process events at a rate suitable for the FPS's system and reduces the number of failed/retried events since the event listener can immediately reply with a successful `200` status.

### Error handling

Rhyza retries the webhook request at increasing intervals if a non-200 status is returned, indicating an error, or the request times out. The first retry occurs after 10 seconds. Additional retries occur after 20 more seconds, then after 30 more seconds, and so on. Rhyza continues to rety until a `200` status is returned.

FSPs can fine-tune timeouts and maximum retries by configuring the environment variables listed below.

<div class="overflow-table">

| Variable            | Type            | Description                                                                                                     |
| ------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |
| `WEBHOOK_TIMEOUT`   | `notifications` | The time, in milliseconds, after which a webhook request times out                                              |
| `WEBHOOK_MAX_RETRY` | `notifications` | The maximum number of retries for a webhook event when a non-200 status is returned or if the request timed out |

</div>

#### Payment intent created

The `payment_intent.created` event indicates a payment intent was created for the recipient. The intent has not yet received funds.

### Payments

<div class="overflow-table">

| Event type                                | Description           |
| ----------------------------------------- | --------------------- |
| [`payment.created`](#payment-created)     | A payment was created |
| [`payment.completed`](#payment-completed) | A payment completed   |
| [`payment.failed`](#payment-failed)       | A payment failed      |

</div>

#### Payment created

The `payment.created` event indicates a payment was created and is awaiting approval. The FSP should verify the sender's account balance and perform any other necessary verifications before approving the payment.

If the sender has insufficient funds or if the payment should otherwise not be fulfilled, the FSP can choose not to call the Admin API's <LinkOut href="/apis/scalar/admin-api#tag/payments/POST/payment-intents/{intentId}/payments/{id}/approve">Approve Payment</LinkOut> endpoint. Otherwise, the FSP should put a hold on the sender's account and approve the payment in Rhyza via the Approve Payment endpoint.

<details>
  <summary>Expand for event sequence</summary>

A payment for $12 was created.

  <Mermaid
    graph={`sequenceDiagram
      participant R as Rhyza

    `}

#### <mark>Payment completed</mark>

The `payment.completed` event indicates that as much as possible was sent to the recipient against their payment intent.

If there is excess liquidity in Rhyza due to differences between the sent and received amounts, withdraw the excess from the payment. What you choose to do with the excess is a business decision. One option is to return the excess to the sender. Another option is to retain the excess as a service fee. Lastly, remove the hold on your sender's account and debit their account on your ledger.

`}

</details>

#### <mark>Payment failed</mark>

The `payment.failed` event indicates the payment failed to send and any retries were unsuccessful. The FSP should withdraw any remaining liquidity from the payment in Rhyza and remove hold from the sender's account.
